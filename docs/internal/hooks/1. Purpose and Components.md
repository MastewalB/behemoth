## **Purpose and Components**

This document explains why Behemoth has a hook system, lists every type that takes part in it, and shows which package each one lives in and why.

---

# **Purpose**

Hooks let a plugin or the application add behaviour to a flow it does not own. Examples:

- reject a sign-up when the email domain is banned (before the user is created)
- add a row to a plugin's own table for every new user, in the same transaction
- demand a second factor before a sign-in completes
- count failed sign-ins and lock the account after too many
- send a welcome email once the user exists

Without hooks, each of these would be an edit to the email/password plugin or to the store. With hooks, the flow stays generic and names the places where others may step in. A TOTP plugin can hook the email/password plugin's sign-in without either package importing the other: both only know the point name `auth.signIn.credentialsVerified`.

The examples above are of three different kinds, and the system keeps them apart:

| Kind | Example | Can it change the outcome? | Phase |
| --- | --- | --- | --- |
| Interceptor | reject a sign-up, rewrite a row | yes: it can rewrite the payload or stop the operation | before |
| Observer of a success | send a welcome email | no, with one exception (below) | after |
| Observer of a rejection | count a failed sign-in | no | failed |

The exception is the after phase of a data point. `data.user.afterCreate` runs inside the write's transaction, and an error there rolls the write back. That makes it part of the write, not an observer. The tiers that produce this difference are described in [2. Hook Taxonomy](<2. Hook Taxonomy.md>).

# **Components**

### **The public contract: `types`**

Everything a plugin author touches is in `types/plugins.go`.

| Type | Kind | Role |
| --- | --- | --- |
| `HookPoint` | `string` | the name of a point |
| `HookPhase` | `string` | `before`, `after` or `failed` |
| `HookPointDef` | struct | a declaration: point, owner, phase, optional audit spec |
| `HookCatalog` | interface | where points are declared and looked up |
| `PluginInitContext` | struct | what `Plugin.Declare` receives; its `Hooks` field is the catalog |
| `HookRegistry` | interface | where handlers are attached to points |
| `HookOptions`, `HookPriority` | struct, `int` | a handler's ordering wishes |
| `BeforeHookFunc`, `AfterHookFunc`, `FailedHookFunc` | func types | the handler signature of each phase |
| `FailureReason` | struct | what a failed handler is told |
| `HookContext` | struct | what every handler receives |
| `Dispatcher` | interface | runs the chain of a point |
| `WithLifecycle` | generic func | wraps a flow with its before, after and failed points |
| `ContextWithHookValues`, `HookValuesFrom`, `NestedHookValues`, `BeginOperation`, `AsOperation` | funcs | carry an operation's `Values` on the context, so nested operations start from a copy |
| `KahnSort` | func | the topological sort used for plugin order and for handler order |

Two `Plugin` methods connect a plugin to the system:

```go
Declare(ic *PluginInitContext) error // ic.Hooks.Declare(...)
Register(reg HookRegistry) error     // reg.OnBefore(...), reg.OnAfter(...), reg.OnFailed(...)
```

The application has no `Plugin`. It registers handlers through `BootConfig.Hooks`, a `func(reg types.HookRegistry) error`.

### **The names: `types/hooks`**

`types/hooks/hooks.go` holds two groups of constants and no logic:

- the `Hook...` constants: the name of every point core declares (`HookSignUpBefore`, `HookUserAfterCreate`, ...)
- the `HookValue...` constants: keys used in payloads and in `HookContext.Values` (`HookValueUserID`, `HookValueIPAddress`, ...)

The value keys are a shared vocabulary. The session manager puts the user agent in the `auth.session.beforeCreate` payload under `HookValueUserAgent` and reads it back from the same key afterwards, so a handler that rewrites it has to use that key. They are plain `string` constants because payloads are `behemoth.M` (`map[string]any`), and a named type would need a conversion at every use.

### **The implementations: `types/init`**

`types/init/init.go` holds the concrete types. None of them is reachable from a plugin except through the interfaces above.

| Type or function | Implements | Role |
| --- | --- | --- |
| `DefaultHookCatalog` | `types.HookCatalog` | a map of declared points behind a lock, with `Freeze` |
| `scopedHookCatalog` | `types.HookCatalog` | wraps the catalog for one declarer and stamps its name as `Owner` |
| `CoreDeclareHookPoints` | | declares core's points |
| `DefaultHookRegistry` | | collects handlers per point, unordered; reached only through `scopedHookRegistry` |
| `scopedHookRegistry` | `types.HookRegistry` | wraps the registry for one owner and stamps its name on each handler |
| `registeredHandler` | | one handler with its owner and ordering options |
| `freezeAllHookChains`, `resolvePointOrder`, `topoSortBucket` | | turn the registry's lists into ordered chains |
| `DefaultDispatcher` | `types.Dispatcher` | runs chains; also checks rate limits and records audit events |
| `Prepare`, `Boot` | | run the stages in order and wire the parts together |

`types/init/datahooks.go` holds the bridge to the store:

| Type or function | Implements | Role |
| --- | --- | --- |
| `dataHooks` | `store.Hooks` | turns a table write reported by the store into a dispatch |
| `tableHookPoints`, `coreDataHookPoints` | | which points a table fires |
| `checkDataHookPoints` | | checks at `Boot` that those points are declared with the right phase |

### **The store side: `store`**

| Type or function | Role |
| --- | --- |
| `store.Hooks` | the interface the store calls around a write (`Fires`, `Begin`, and a before and after method for create and update); knows tables and rows, not hook points |
| `noHooks` | the default implementation: fires nothing |
| `Store.create`, `Store.update`, `Store.hooked` | the write paths that call `Hooks` |
| `Store.Transaction`, `Store.AfterCommit`, `commitQueue` | what the after-commit points are built on |

### **The firing sites**

The code that calls the dispatcher:

| Firing site | File | Points |
| --- | --- | --- |
| `dataHooks` | `types/init/datahooks.go` | `data.user.*` |
| `DefaultSessionManager` | `transport/session.go` | `auth.session.*` |
| `DefaultTokenManager` | `transport/token.go` | `token.*` |
| email/password plugin | `plugins/emailpassword/email-and-password.go` | `auth.signUp.*`, `auth.signIn.*`, `auth.signOut.*` |

### **Neighbours**

- **Rate limiter.** `RunBefore` asks the `RateLimiter` whether the point's rules allow the call before it runs any handler. See [`../ratelimit/rate_limiter.md`](../ratelimit/rate_limiter.md).
- **Telemetry.** The dispatcher logs handler errors through `Telemetry.Logger` and records audit events through `Telemetry.Audit` for points declared with an `AuditSpec`.
- **Router.** It puts the `RequestContext` on the request's `context.Context`, which is how a data hook learns which request caused the write. See [3. Hook Context](<3. Hook Context.md>).

# **How the parts are connected**

```
                         Prepare                                   Boot
            ┌───────────────────────────────┐   ┌──────────────────────────────────────────┐
 core    ──►│ scopedHookCatalog("core")     │   │                                          │
 plugin  ──►│ scopedHookCatalog(<plugin>)   │   │ plugin ──► scopedHookRegistry(<plugin>)  │
            │            │                  │   │ app    ──► scopedHookRegistry(<app>)     │
            │            ▼                  │   │                  │                       │
            │   DefaultHookCatalog ─ Freeze ├──►│                  ▼                       │
            └───────────────────────────────┘   │        DefaultHookRegistry               │
                                                │                  │ freezeAllHookChains   │
                                                │                  ▼                       │
                                                │   frozenChains: point → []handler        │
                                                │                  │                       │
                                                │                  ▼                       │
                                                │   DefaultDispatcher(catalog, chains,     │
                                                │                     rateLimiter, tel)    │
                                                └──────────────────┬───────────────────────┘
                                                                   │ AuthContext.Dispatcher
                 ┌───────────────────────┬─────────────────────────┼──────────────────────┐
                 ▼                       ▼                         ▼                      ▼
        dataHooks (store.Hooks)   DefaultSessionManager    DefaultTokenManager     plugin flows
                 ▲
                 │ BeforeCreate, AfterCreate, ...
               Store
```

### **Why the packages are split this way**

`types` imports `store`, because `AuthContext` holds a `*store.Store` and `HookContext.Tx` is one. So `store` can't import `types`, and it can't name `Dispatcher`, `HookPoint` or `HookContext`.

The store declares what it needs as its own small interface, `store.Hooks`, in terms it already knows: a table name, a row, a model. `types/init` imports both packages, so the adapter `dataHooks` lives there. This follows the repository rule of defining an interface where it is consumed.

| Package | Imports | Knows about |
| --- | --- | --- |
| `store` | neither `types` nor `types/init` | tables, rows, `store.Hooks` |
| `types` | `store` | hook points, contexts, `Dispatcher` |
| `types/hooks` | `types` | point names, value keys |
| `types/init` | `store`, `types`, `types/hooks`, `transport` | everything; builds and connects it |
| `transport`, plugins | `types`, `types/hooks`, `store` | `Dispatcher` as an interface |

### **Wiring order in `Boot`**

Some parts need each other, and `Boot` builds them in the one order that works:

1. the registry, then every `Register`, then `BootConfig.Hooks`
2. `freezeAllHookChains`
3. the rate limiter, with a store of its own that has no hooks
4. the dispatcher
5. the `AuthContext`, holding the dispatcher
6. `checkDataHookPoints`
7. the store, with `dataHooks{ac: ac, ...}`, assigned to `ac.Store`
8. the token and session managers, which get the store, the dispatcher and `ac`. The session manager also gets the client-IP configuration the route rate limiter uses.
9. every plugin's `Init(ac)`

`dataHooks` holds the `AuthContext` and the `AuthContext` holds the store that holds `dataHooks`. The cycle is harmless because `dataHooks` reads `ac.Dispatcher` when a write happens, not when it is built.

The rate limiter's counter store is built without `WithHooks`. Counter writes fire no data hooks and open no transaction. If the limiter used the hooked store, a counter increment inside `RunBefore` could itself fire hooks.

Handlers are registered in step 1, before the `AuthContext` exists. A handler that needs the store or a manager reads it from `hctx.Auth` when it runs, or from a field its plugin sets in `Init`. All handlers are in place before the first `Init` runs, so a write made from `Init` already fires them.

# **Limits to know**

- `[Not built]` Introspection. There is no API to list the handlers of a point in their resolved order. The frozen chains are a private field of `DefaultDispatcher`.
- `[Not built]` A retry or failure reporter for after handlers. Errors are logged through `Telemetry.Logger` and nothing else happens.
- `[Not built]` The application can register handlers (`BootConfig.Hooks`) but can't declare points. `PrepareConfig` has a `Schema` callback and no counterpart for hook points. An application that wants points of its own writes a plugin.
- `[Not built]` Delete points. `Store.DeleteUser` calls the adapter directly and fires nothing.
- Only `users` fires data hooks. See [6. Data Hooks](<6. Data Hooks.md>).
