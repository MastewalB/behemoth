## **Hook Context**

This document explains what a handler receives: the `HookContext`, and the payload, result or reason that comes with it. It covers who builds the context at each firing site, how the HTTP request reaches a handler that was fired from the store, and what happens to a payload after a before chain returns it.

---

# **`HookContext`**

```go
type HookContext struct {
	Ctx     context.Context
	Point   HookPoint
	Phase   HookPhase
	Auth    *AuthContext
	Tx      *store.Store
	Values  behemoth.M
	Request *RequestContext
}
```

| Field | Meaning | Nil or empty when |
| --- | --- | --- |
| `Ctx` | cancellation and deadlines. Inside a data hook it is the transaction's context. | never |
| `Point`, `Phase` | which point is being dispatched | the email/password flows leave them empty (see below) |
| `Auth` | the `AuthContext`: store, managers, dispatcher, crypto, telemetry | never under `Boot` |
| `Tx` | the store bound to the write's transaction | every Tier 2 point, and the committed data points |
| `Values` | scratch space for handlers to leave notes for each other | never; the firing site allocates it |
| `Request` | the HTTP request being handled | the operation was not started by a request (a CLI, a job) |

The firing site builds the context and passes it to the dispatcher. `DefaultDispatcher` never changes it: it reads `hctx.Ctx` for logging, rate limiting and audit, hands `hctx` to the rate limiter's `KeyFunc`, and passes the same pointer to every handler in the chain.

### **Why not `RequestContext`**

A route handler gets a `RequestContext`: an `*http.Request` and a response to write. Hooks fire from code below the HTTP layer, and that code runs without a request too:

- a CLI or a seed script calling `Store.CreateUser`
- a background job revoking sessions
- one plugin calling another plugin's exported function

If a handler's context required a request, each of these callers would have to invent one. `HookContext` therefore carries the request as an optional field. A handler that needs the IP address checks `hctx.Request != nil` first.

`Ctx` is the one context to use. When `Request` is set, `Request.Ctx` is the request's context, and inside a data hook `hctx.Ctx` is derived from it and may also carry the transaction (on MongoDB the session travels in the context). A handler that calls the store or an adapter passes `hctx.Ctx`.

# **Who builds it**

There are three firing sites and three ways the context is built.

### **Data hooks: `dataHooks.hookContext`**

`types/init/datahooks.go`. One context per dispatch.

| Field | Value |
| --- | --- |
| `Ctx` | the context of the store call. Inside `Store.Transaction` that is the transaction callback's context. |
| `Point`, `Phase` | the point being dispatched and the phase the store fires it in |
| `Auth` | the `AuthContext` `Boot` gave to `dataHooks` |
| `Tx` | the transaction-bound store, or nil for `created` and `updated` |
| `Values` | a fresh map. For update points it holds the row's id (below). |
| `Request` | `types.RequestFrom(ctx)` |

An update's payload holds only the columns being changed, so the handler could not tell which row is meant. `dataHooks` puts the id in `Values` under the table's `idValue` key, which is `hooks.HookValueUserID` for `users`:

```go
reg.OnBefore(hooks.HookUserBeforeUpdate, func(hctx *types.HookContext, changes behemoth.M) (behemoth.M, error) {
	userID := hctx.Values[hooks.HookValueUserID]
	// ...
	return changes, nil
}, nil)
```

`BeforeUpdate` gets the id from the caller. `AfterUpdate` and `UpdateCommitted` take it from the stored row (`updated.PrimaryKeyField()`). Create points don't set it: the id is in the row.

### **Managers: `hookContext` in `transport/session.go`**

The session and token managers share one helper. It builds a context per dispatch with the point, the phase, the `AuthContext` their constructor received, a fresh `Values` and `RequestFrom(ctx)`. `Tx` is nil.

The before and the after point of one operation get two contexts, so a note left in `Values` by a `beforeCreate` handler is not visible to an `afterCreate` handler.

### **Plugin flows: built from the `RequestContext`**

The email/password route handlers build the context themselves:

```go
hctx := &types.HookContext{Ctx: rctx.Ctx, Auth: rctx.Auth, Request: rctx, Values: behemoth.M{}}
user, err := p.signUp(hctx, body)
```

This one context is passed to `WithLifecycle` and from there to the flow body, so it serves every dispatch of the flow: `auth.signIn.before`, `auth.signIn.credentialsVerified`, `auth.signIn.failed` and `auth.signIn.after` all receive the same pointer. Two things follow:

- **`Point` and `Phase` are empty.** Nothing sets them: the handler does not, `WithLifecycle` does not, and the dispatcher never writes to the context. A handler on these points, or a rate-limit `KeyFunc`, can't read the point from the context.
- **`Values` lasts for the whole flow.** A note left by a `signIn.before` handler is still there for `signIn.after`. This differs from the two sites above, and from the field's doc comment, which describes `Values` as scoped to one chain.

Both are recorded in [`../../ongoing.md`](../../ongoing.md).

The dispatches nested inside the flow build their own contexts. When `signInBody` calls `SessionManager.Create`, the `auth.session.beforeCreate` handlers get the manager's fresh context, not the flow's.

### **The three compared**

| | data hooks | managers | email/password flows |
| --- | --- | --- | --- |
| Built | per dispatch | per dispatch | once per request |
| `Point`, `Phase` | set | set | empty |
| `Tx` | set inside the transaction | nil | nil |
| `Values` scope | one chain | one chain | the whole flow |
| `Request` | from the context | from the context | the handler's own `RequestContext` |

# **How the request reaches a data hook**

The store's methods take a `context.Context` and nothing else. `Store.CreateUser(ctx, u)` has no parameter for a request, and `store` can't import `types` to name one. The request travels in the context:

1. `Router.withRequestScope` wraps every route. It calls `types.ContextWithRequest(ctx, rctx)` and stores the result in `rctx.Ctx`.
2. The route handler passes `rctx.Ctx` down: to a flow, to the store, to a manager.
3. `Store.Transaction` hands the adapter's transaction context to its callback. That context is derived from the caller's, so the value is still there.
4. `dataHooks.hookContext` and the managers' `hookContext` call `types.RequestFrom(ctx)` and put the result in `HookContext.Request`.

Outside a request nobody called `ContextWithRequest`, `RequestFrom` returns nil, and `Request` is nil.

`TestDataHooksSeeTheRequestBeingHandled` covers the path through a real `Boot`. A test that calls a flow directly has to do step 1 itself (`types.ContextWithRequest(req.Context(), rctx)`), otherwise data hooks and manager hooks see no request.

Only the request travels this way. Everything else a handler needs is a field of the context or comes through `Auth`.

### **The session manager reads it too**

`DefaultSessionManager.Create` uses the same lookup for the session's IP address and user agent (`requestMeta` in `transport/session.go`):

| `SessionMeta` field | Request on the context | Value used |
| --- | --- | --- |
| set by the caller | any | the caller's value |
| empty | yes | `types.ClientIP(request, ipCfg)`, `request.UserAgent()` |
| empty | no | empty |

`SessionConfig.CaptureIPAndAgent` is applied afterwards: when it is off, both are cleared whatever their source. The values then go into the `auth.session.beforeCreate` payload and onto the session row.

`ipCfg` is the `ClientIPConfig` `Boot` builds from `RouterConfig.TrustedProxies` and `ClientIPHeader`. The route rate limiter gets the same one, so a session records the address a per-IP limit counted. Behind a trusted proxy that is the forwarded client, not the proxy.

A caller of `Create` passes the context it was given and sets only `State`. `signInBody` does this, which is why sign-in runs without an HTTP request: the session then has no IP address or user agent.

# **`Values`, payload, `Request.Values`**

Three maps are in reach of a handler. They differ in scope and in who reads them afterwards.

| Map | Scope | Read by | Use it for |
| --- | --- | --- | --- |
| payload (before handlers) | one chain | the next handler, then the firing site | data the operation should act on |
| `hctx.Values` | one chain (the whole flow in the email/password plugin) | later handlers | notes between handlers, for example "password strength already checked" |
| `hctx.Request.Values` | the HTTP request | middleware, route handlers, any hook of the request | data tied to the request, for example the session id a middleware resolved |

The firing site never reads `hctx.Values` back. A value a handler wants the operation to use has to go in the payload.

# **What comes with the context**

### **Before: a payload**

```go
type BeforeHookFunc func(hctx *HookContext, payload behemoth.M) (behemoth.M, error)
```

- The payload is always a `behemoth.M`, in both tiers. A typed input is converted first (below).
- The handler returns the payload to continue with, changed or not. The returned map is passed to the next handler.
- A non-nil error stops the chain and the operation. There is no separate abort flag.
- The error is returned to the caller unchanged, so it should be one of the `behemotherr` types the HTTP layer can map to a status.

The dispatcher does not check the returned map. A handler that returns `nil, nil` passes a nil map to the next handler, and a write to a nil map panics there. The panic is recovered and stops the chain as an internal error.

How a typed value becomes a payload:

| Firing site | To `M` | Back |
| --- | --- | --- |
| `Store.create` | the model's `ToMap` | `checkColumns`, then the model's `FromMap` |
| `Store.update` | a copy of the caller's changes | `checkUpdate` |
| `WithLifecycle` | `structToM`: `ToMap` if the input is `behemoth.Serializable`, otherwise a JSON round trip | `mFromStruct`: `FromMap`, otherwise JSON |
| managers, `signInBody`, `SignOut` | a map literal built for the point | individual keys |

The JSON round trip means a `WithLifecycle` input is seen by handlers under its JSON field names, and a field without a JSON representation is lost. Sign-in's input is `EmailAndPasswordCredentials`, so handlers see `email` and `password`.

### **What the firing site does with the returned payload**

A before handler can always stop the operation. Whether its rewrite has an effect depends on what the firing site reads back:

| Point | Read back |
| --- | --- |
| `data.user.beforeCreate` | the whole row. An unknown column is a validation error. |
| `data.user.beforeUpdate` | the whole change set. An unknown column or the primary key is a validation error. |
| `auth.signUp.before`, `auth.signIn.before` | the whole payload, as the flow's input |
| `auth.signIn.credentialsVerified` | the key `requireStepUp`. `true` makes the session pending instead of active. |
| `auth.session.beforeCreate` | `HookValueUserAgent` |
| `auth.session.beforeRevoke`, `token.beforeIssue`, `auth.signOut.before` | nothing. The returned payload is dropped; the point can only veto. |

### **After: a result**

```go
type AfterHookFunc func(hctx *HookContext, result any) error
```

`result` is whatever the firing site produced, typed as `any`. The handler asserts the type it expects:

| Points | Result type |
| --- | --- |
| `data.user.afterCreate`, `afterUpdate`, `created`, `updated`, `auth.signUp.after` | `*models.User` |
| `auth.signIn.after` | `*emailpassword.SignInResult` |
| `auth.session.afterCreate`, `afterRevoke` | `*models.Session` |
| `token.afterIssue`, `token.consumed` | `*types.Token` |
| `auth.signOut.after` | nil |

What a returned error does depends on the dispatcher method the firing site used. See [5. Hook Dispatching](<5. Hook Dispatching.md>).

The result is a pointer to the same value the firing site returns to its caller. A handler that changes it changes what the caller gets, and for the in-transaction data points it changes the caller's model without changing the stored row. Nothing prevents this. Treat the result as read-only.

### **Failed: a reason**

```go
type FailedHookFunc func(hctx *HookContext, reason FailureReason) error

type FailureReason struct {
	Code  string
	Cause error
}
```

`Code` is a short string chosen by the firing site (`invalidCredentials`, `userNotFound`, `rejectedByHook`, ...). `Cause` is the underlying error when there is one: the before handler's error for `rejectedByHook` and `secondFactorRejected`, the classified error for `token.failed`. For a plain business rejection it is nil.

Failed points are fired for business rejections only. An infrastructure error (the database is down, the hasher failed) is returned to the caller without a `Fail` call, so a lockout counter built on `auth.signIn.failed` does not count outages as wrong passwords. Each firing site is responsible for keeping that line. `signInBody` shows it (shortened):

```go
user, err := ac.Store.FindUserByEmail(hctx.Ctx, creds.Email)
if err != nil {
	if behemotherr.IsNotFound(err) {
		dispatcher.Fail(hctx, hooks.HookSignInFailed, types.FailureReason{Code: "userNotFound"})
		return nil, errors.New("invalid email or password")
	}
	return nil, err // not a rejection: no Fail
}
```

# **Design decisions**

### Hooks get their own context type
**Context:** Route handlers already receive a `RequestContext`. Hook handlers need much of the same (a context, the `AuthContext`, a scratch map).
**Options considered:**
- *Reuse `RequestContext`.* One type to learn. Every firing site without a request would have to build an empty one, and handlers would need nil checks on `Request.Header` and the response recorder in code that has nothing to do with HTTP.
- *A separate `HookContext` with the request as an optional field.* A second type. Firing sites below the HTTP layer build it from what they have, and the nil `Request` states plainly that there is none.
**Decision:** The separate type. It also gives a place for fields a request context has no use for: `Point`, `Phase` and `Tx`.

### The request travels in the `context.Context`
**Context:** A data hook should be able to see the request that caused the write (IP address, headers), but the store's API takes a `context.Context` and `store` can't import `types`.
**Options considered:**
- *Add a request parameter to the store's write methods.* Explicit. It puts an HTTP type in the data layer's signatures, which the import direction forbids, and every caller without a request passes nil.
- *Carry the request in the context.* The store's API is untouched. A context value is implicit: nothing in a signature shows that it is expected, and a caller that passes a fresh context loses it.
**Decision:** The context, for the request only. The request is request-scoped by definition, which is what context values are for. Other dependencies stay explicit, in line with the repository rule to prefer visible parameters.
**Revisit if:** more values are proposed for the same route. Each one makes the implicit contract wider.

### The session manager takes the IP address and user agent from the request
**Context:** `SessionManager.Create` received both in `SessionMeta`, and each caller extracted them. The email/password sign-in read `hctx.Request.Request.RemoteAddr` without a nil check, so it panicked outside a request, and behind a proxy it stored the proxy's address.
**Options considered:**
- *Keep the extraction in each caller.* Explicit. Every sign-in method (OAuth, magic link, a second factor) repeats it and has to get the nil check and the proxy rule right.
- *A helper the caller invokes*, for example `SessionMetaFrom(rctx)`. Still explicit, and the rules live in one function. A new caller can forget it, and nothing reports a session without an address.
- *The manager reads the request from the context, with `SessionMeta` as an override.* One place for the rules, next to `CaptureIPAndAgent`, and the `Create` signature stays. The dependency is implicit: a caller that passes a fresh context gets a session without an address.
**Decision:** The manager reads it. The request is the one value that already travels in the context, and the manager already reads it there for its hook contexts. The `SessionMeta` fields stay for a caller without a request that knows the values.
**Revisit if:** sessions without an address turn up from callers that dropped the context. A warning log in `Create` when capture is on and no request is found would be the first step.
