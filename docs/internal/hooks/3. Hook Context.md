## **Hook Context**

This document explains what a handler receives: the `HookContext`, and the payload, result or reason that comes with it. It covers who builds the context at each firing site, how long `Values` last and how nested operations inherit them, how the HTTP request reaches a handler that was fired from the store, and what happens to a payload after a before chain returns it.

---

# **`HookContext`**

```go
type HookContext struct {
	Ctx     context.Context
	Point   HookPoint
	Phase   HookPhase
	Auth    *AuthContext
	Tx      *store.Store
	Values  behemoth.M
	Request *RequestContext
}
```

| Field | Meaning | Nil or empty when |
| --- | --- | --- |
| `Ctx` | cancellation and deadlines. Inside a data hook it is the transaction's context. | never |
| `Point`, `Phase` | which point is being dispatched. The dispatcher sets both. | never, for a handler |
| `Auth` | the `AuthContext`: store, managers, dispatcher, crypto, telemetry | never under `Boot` |
| `Tx` | the store bound to the write's transaction | every Tier 2 point, and the committed data points |
| `Values` | scratch space for handlers to leave notes for each other, for the length of one operation | never, for a handler |
| `Request` | the HTTP request being handled | the operation was not started by a request (a CLI, a job) |

The firing site builds the context and passes it to the dispatcher. `DefaultDispatcher` does not change the site's context. It gives the handlers a shallow copy (`forPoint`) with `Point` and `Phase` set to the point being dispatched:

- A site may leave both fields empty. A flow that uses one context for all of its points does.
- A site can't dispatch one point with a context that names another.
- The copy shares the `Values` map, so handlers of different points of one operation write to the same map.
- A nil `Values` is replaced with an empty map in the copy, so a handler's write can't panic. Notes written to it last for that dispatch only.

The rate limiter's `KeyFunc` and the audit recorder get the same copy.

### **Why not `RequestContext`**

A route handler gets a `RequestContext`: an `*http.Request` and a response to write. Hooks fire from code below the HTTP layer, and that code runs without a request too:

- a CLI or a seed script calling `Store.CreateUser`
- a background job revoking sessions
- one plugin calling another plugin's exported function

If a handler's context required a request, each of these callers would have to invent one. `HookContext` therefore carries the request as an optional field. A handler that needs the IP address checks `hctx.Request != nil` first.

`Ctx` is the one context to use. When `Request` is set, `Request.Ctx` is the request's context, and inside a data hook `hctx.Ctx` is derived from it and may also carry the transaction (on MongoDB the session travels in the context). A handler that calls the store or an adapter passes `hctx.Ctx`.

# **Who builds it**

There are three kinds of firing site. They differ in where the context comes from, and all follow the same rule for `Values` (next section).

### **Data hooks: `dataHooks.hookContext`**

`types/init/datahooks.go`. One context per dispatch.

| Field | Value |
| --- | --- |
| `Ctx` | the context of the store call. Inside `Store.Transaction` that is the transaction callback's context. For `created` and `updated` it is the context `Store.Transaction` was called with. |
| `Point`, `Phase` | the point being dispatched and the phase the store fires it in |
| `Auth` | the `AuthContext` `Boot` gave to `dataHooks` |
| `Tx` | the transaction-bound store, or nil for `created` and `updated` |
| `Values` | the write's map, shared by all of its points. For update points it holds the row's id (below). |
| `Request` | `types.RequestFrom(ctx)` |

An update's payload holds only the columns being changed, so the handler could not tell which row is meant. `dataHooks` puts the id in `Values` under the table's `idValue` key, which is `hooks.HookValueUserID` for `users`:

```go
reg.OnBefore(hooks.HookUserBeforeUpdate, func(hctx *types.HookContext, changes behemoth.M) (behemoth.M, error) {
	userID := hctx.Values[hooks.HookValueUserID]
	// ...
	return changes, nil
}, nil)
```

`BeforeUpdate` gets the id from the caller. `AfterUpdate` takes it from the stored row (`updated.PrimaryKeyField()`), and the `updated` point inherits it with the write's map. Create points don't set it: the id is in the row.

### **Managers: `hookContext` in `transport/session.go`**

The session and token managers share one helper. It builds a context per dispatch with the point, the phase, the `AuthContext` their constructor received, the operation's `Values` and `RequestFrom(ctx)`. `Tx` is nil.

Each manager method that fires points opens its operation first, with `ctx = types.BeginOperation(ctx)`: `Create`, `revokeModel`, `Issue` and `Consume`.

### **Plugin flows: one context for the flow**

The email/password plugin builds one context per flow call (`Plugin.operation`) and hands it to the flow wrapped by `WithLifecycle`:

```go
func (p *Plugin) SignUp(ctx context.Context, input behemoth.M) (*models.User, error) {
	hctx, err := p.operation(ctx, "emailpassword.SignUp") // Ctx, Auth, Values, Request
	if err != nil {
		return nil, err
	}
	return p.signUp(hctx, input)
}
```

`SignUp` and `SignIn` are exported, and the route handlers call them with `rctx.Ctx`. A CLI, a job or another plugin calls the same methods with its own context. `Request` comes from the context, so it is set for the route and nil for the others.

`WithLifecycle` starts with `types.AsOperation(hctx)` and uses the result for every dispatch of the flow and for the flow body. `auth.signIn.before`, `auth.signIn.credentialsVerified`, `auth.signIn.failed` and `auth.signIn.after` therefore share one `Values`. The flow's context has no `Point` or `Phase`; the dispatcher fills them in for each dispatch.

`SignOut` takes a `HookContext` from its caller and does the same with `AsOperation`.

### **The three compared**

| | data hooks | managers | email/password flows |
| --- | --- | --- | --- |
| Context built | per dispatch | per dispatch | once per flow call |
| `Point`, `Phase` set by | the site and the dispatcher | the site and the dispatcher | the dispatcher |
| `Tx` | set inside the transaction | nil | nil |
| Operation opened by | `dataHooks.Begin`, once per write | `BeginOperation` in the method | `Plugin.operation` and `AsOperation` |
| `Request` | from the context | from the context | from the context |

# **The scope of `Values`**

`Values` lasts for one operation. An operation is one call at one firing site: a sign-in, a session create, a write to `users`. The before, after and failed points that site fires for the call share one map.

| Operation | Points that share a map |
| --- | --- |
| a sign-up | `auth.signUp.before`, `.failed`, `.after` |
| a sign-in | `auth.signIn.before`, `.credentialsVerified`, `.failed`, `.after` |
| a sign-out | `auth.signOut.before`, `.after` |
| a session create | `auth.session.beforeCreate`, `.afterCreate` |
| a session revoke | `auth.session.beforeRevoke`, `.afterRevoke` |
| a token issue | `token.beforeIssue`, `.afterIssue` |
| a token consume | `token.consumed` or `token.failed` |
| a user create | `data.user.beforeCreate`, `.afterCreate`, `.created` |
| a user update | `data.user.beforeUpdate`, `.afterUpdate`, `.updated` |

### **Nested operations**

Operations nest. A sign-up writes a user; a sign-in creates a session. The inner operation begins with a copy of the outer one's `Values`:

- its handlers read what the outer operation's handlers left
- what its handlers write stays in the copy and does not reach the outer map
- a second inner operation starts from the outer map again, without the first one's notes

This is the direction a `context.Context` works in: a derived context sees its parent's values, and the parent never sees the child's.

The copy is shallow (`maps.Copy`). A pointer or a map stored as a value is shared with the outer operation.

### **An example: an invite code**

An invite plugin accepts `inviteCode` at sign-up and attaches the new user to the invite.

| Step | Point | Handler | `Values` it sees |
| --- | --- | --- | --- |
| 1 | `auth.signUp.before` | reads `payload["inviteCode"]`, looks the invite up, sets `Values["invite.id"]` | `{}` |
| 2 | `data.user.beforeCreate` | | `{invite.id}` (a copy) |
| 3 | `data.user.afterCreate` | links the user to the invite through `hctx.Tx`, in the user's transaction | `{invite.id}` |
| 4 | `auth.signUp.after` | sends the "invite accepted" email | `{invite.id}` |

An after handler receives the result of the operation and not its input, so the invite's id has to be carried from step 1. The caller of the flow never touches `Values`: it passes the code as input, the same way from the HTTP route and from a CLI. Step 3 is why nested operations see the outer values. Without that the link could only be made in step 4, after the commit.

`TestEmailPasswordFlowsShareValuesAndRunWithoutARequest` runs this shape under a real `Boot`.

Keys should start with the owner's name (`invite.id`). All handlers of an operation share the map, and nested operations inherit it.

### **How the scope travels**

The store and the managers take a `context.Context`, so the operation's map travels there, next to the request. Five functions in `types/plugins.go` do the work:

| Function | Does | Used by |
| --- | --- | --- |
| `ContextWithHookValues(ctx, values)` | puts an operation's map on a context | `AsOperation`, `BeginOperation`, the committed dispatch in `dataHooks` |
| `HookValuesFrom(ctx)` | returns the map of the operation `ctx` belongs to, or nil | `hookContext` in `dataHooks` and in `transport` |
| `NestedHookValues(ctx)` | returns a copy of that map, or an empty one | `BeginOperation`, `AsOperation`, `Plugin.operation` |
| `BeginOperation(ctx)` | opens a nested operation: the two above combined | the managers, `dataHooks.Begin` |
| `AsOperation(hctx)` | turns a `HookContext` into an operation: fills a nil `Values` and puts the map on `Ctx` | `WithLifecycle`, `SignOut` |

A sign-up then runs like this:

1. `Plugin.operation` builds the flow's context with `Values: NestedHookValues(ctx)`. Called from a route there is no enclosing operation, so the map is empty.
2. `WithLifecycle` calls `AsOperation`. `hctx.Ctx` now carries the flow's map.
3. `signUpBody` calls `ac.Store.Transaction(hctx.Ctx, ...)` and `tx.CreateUser(ctx, user)`.
4. `Store.hooked` calls `dataHooks.Begin(ctx, "users")`, which calls `BeginOperation`: the write's context carries a copy of the flow's map.
5. `dataHooks.hookContext` reads that copy with `HookValuesFrom` for each of the write's dispatches.

A firing site of your own follows the managers: call `BeginOperation` once at the top of the method, pass the returned context on, and build each `HookContext` with `Values: types.HookValuesFrom(ctx)`.

### **Where the link breaks**

- **A fresh context.** A callee that is handed `context.Background()` instead of the caller's context starts an operation with empty values. Nothing reports it.
- **A dispatcher call with a hand-built context.** A site that builds a `HookContext` with its own empty map and never puts it on a context gets one map per context it builds, and its nested operations inherit nothing.
- **Goroutines.** The map is not synchronized. An operation that fans out must not let two goroutines dispatch with the same `Values`.

# **How the request reaches a data hook**

The store's methods take a `context.Context` and nothing else. `Store.CreateUser(ctx, u)` has no parameter for a request, and `store` can't import `types` to name one. The request travels in the context:

1. `Router.withRequestScope` wraps every route. It calls `types.ContextWithRequest(ctx, rctx)` and stores the result in `rctx.Ctx`.
2. The route handler passes `rctx.Ctx` down: to a flow, to the store, to a manager.
3. `Store.Transaction` hands the adapter's transaction context to its callback. That context is derived from the caller's, so the value is still there.
4. `dataHooks.hookContext` and the managers' `hookContext` call `types.RequestFrom(ctx)` and put the result in `HookContext.Request`.

Outside a request nobody called `ContextWithRequest`, `RequestFrom` returns nil, and `Request` is nil.

`TestDataHooksSeeTheRequestBeingHandled` covers the path through a real `Boot`. A test that calls a flow directly has to do step 1 itself (`types.ContextWithRequest(req.Context(), rctx)`), otherwise data hooks and manager hooks see no request.

The request and the operation's `Values` (previous section) are the two things that travel this way. Everything else a handler needs is a field of the context or comes through `Auth`.

### **The session manager reads it too**

`DefaultSessionManager.Create` uses the same lookup for the session's IP address and user agent (`requestMeta` in `transport/session.go`):

| `SessionMeta` field | Request on the context | Value used |
| --- | --- | --- |
| set by the caller | any | the caller's value |
| empty | yes | `types.ClientIP(request, ipCfg)`, `request.UserAgent()` |
| empty | no | empty |

`SessionConfig.CaptureIPAndAgent` is applied afterwards: when it is off, both are cleared whatever their source. The values then go into the `auth.session.beforeCreate` payload. When capture is on, what the chain returns under the two keys goes onto the session row. When it is off the row stays empty whatever a handler set.

`ipCfg` is the `ClientIPConfig` `Boot` builds from `RouterConfig.TrustedProxies` and `ClientIPHeader`. The route rate limiter gets the same one, so a session records the address a per-IP limit counted. Behind a trusted proxy that is the forwarded client, not the proxy.

A caller of `Create` passes the context it was given and sets only `State`. `signInBody` does this, which is why `Plugin.SignIn` runs without an HTTP request: the session then has no IP address or user agent.

# **`Values`, payload, `Request.Values`**

Three maps are in reach of a handler. They differ in scope and in who reads them afterwards.

| Map | Scope | Read by | Use it for |
| --- | --- | --- | --- |
| payload (before handlers) | one chain | the next handler, then the firing site | data the operation should act on |
| `hctx.Values` | one operation, and as a copy the operations nested in it | handlers | notes between handlers: an invite id resolved from the input, a start time, "password strength already checked" |
| `hctx.Request.Values` | the HTTP request | middleware, route handlers, any hook of the request | data tied to the request, for example the session id a middleware resolved |

The firing site never reads `hctx.Values` back. A value a handler wants the operation to use has to go in the payload.

`hctx.Request.Values` is wider than `hctx.Values` and exists only when there is a request. A handler that has to work for a flow called from a job uses `hctx.Values`.

# **What comes with the context**

### **Before: a payload**

```go
type BeforeHookFunc func(hctx *HookContext, payload behemoth.M) (behemoth.M, error)
```

- The payload is always a `behemoth.M`, in both tiers. A typed input is converted first (below).
- The handler returns the payload to continue with. The returned map is passed to the next handler.
- A nil map with a nil error means "no change". The chain continues with the map the handler received, including what the handler changed in place.
- A non-nil error stops the chain and the operation. There is no separate abort flag.
- The error is returned to the caller unchanged, so it should be one of the `behemotherr` types the HTTP layer can map to a status.

`RunBefore` keeps the payload non-nil from end to end. A nil input from the firing site starts the chain as an empty map, so a handler's first write can't panic, and the firing site gets a map back whenever the error is nil. Compare the two ways a validator can end:

```go
return payload, nil // continue with payload
return nil, nil     // the same: continue with the payload this handler received
```

An empty map is a rewrite, not "no change": `return behemoth.M{}, nil` continues with no keys.

How a typed value becomes a payload:

| Firing site | To `M` | Back |
| --- | --- | --- |
| `Store.create` | the model's `ToMap` | `checkColumns`, then the model's `FromMap` |
| `Store.update` | a copy of the caller's changes | `checkUpdate` |
| `WithLifecycle` | `structToM`: `ToMap` if the input is `behemoth.Serializable`, otherwise a JSON round trip | `mFromStruct`: `FromMap`, otherwise JSON |
| managers, `signInBody`, `SignOut` | a map literal built for the point | individual keys |

The JSON round trip means a `WithLifecycle` input is seen by handlers under its JSON field names, and a field without a JSON representation is lost. An input that needs another payload shape implements `behemoth.Serializable`. Sign-in's `EmailAndPasswordCredentials` does: its `ToMap` puts the keys of its `Extra` map next to `email` and `password`, and its `FromMap` takes them apart again. See [the plugin's doc](../plugins/emailpassword.md).

### **What the firing site does with the returned payload**

A before handler can always stop the operation. Whether its rewrite has an effect depends on what the firing site reads back:

| Point | Read back |
| --- | --- |
| `data.user.beforeCreate` | the whole row. An unknown column is a validation error. |
| `data.user.beforeUpdate` | the whole change set. An unknown column or the primary key is a validation error. |
| `auth.signUp.before`, `auth.signIn.before` | the whole payload, as the flow's input |
| `auth.signIn.credentialsVerified` | the key `requireStepUp`. `true` makes the session pending instead of active. |
| `auth.session.beforeCreate` | `HookValueIPAddress` and `HookValueUserAgent`, when `SessionConfig.CaptureIPAndAgent` is on. Nothing when it is off. `HookValueUserID` and `HookValueState` are never read back. |
| `auth.session.beforeRevoke`, `token.beforeIssue`, `auth.signOut.before` | nothing. The returned payload is dropped; the point can only veto. |

A key is read back with a type assertion (`payload[key].(string)`), so a missing key or a value of another type leaves the site's own value in place.

### **After: a result**

```go
type AfterHookFunc func(hctx *HookContext, result any) error
```

`result` is whatever the firing site produced, typed as `any`. The handler asserts the type it expects:

| Points | Result type |
| --- | --- |
| `data.user.afterCreate`, `afterUpdate`, `created`, `updated`, `auth.signUp.after` | `*models.User` |
| `auth.signIn.after` | `*emailpassword.SignInResult` |
| `auth.session.afterCreate`, `afterRevoke` | `*models.Session` |
| `token.afterIssue`, `token.consumed` | `*types.Token` |
| `auth.signOut.after` | nil |

What a returned error does depends on the dispatcher method the firing site used. See [5. Hook Dispatching](<5. Hook Dispatching.md>).

The result is a pointer to the same value the firing site returns to its caller. A handler that changes it changes what the caller gets, and for the in-transaction data points it changes the caller's model without changing the stored row. Nothing prevents this. Treat the result as read-only.

### **Failed: a reason**

```go
type FailedHookFunc func(hctx *HookContext, reason FailureReason) error

type FailureReason struct {
	Code  string
	Cause error
}
```

`Code` is a short string chosen by the firing site (`invalidCredentials`, `userNotFound`, `rejectedByHook`, ...). `Cause` is the underlying error when there is one: the before handler's error for `rejectedByHook` and `secondFactorRejected`, the classified error for `token.failed`. For a plain business rejection it is nil.

Failed points are fired for business rejections only. An infrastructure error (the database is down, the hasher failed) is returned to the caller without a `Fail` call, so a lockout counter built on `auth.signIn.failed` does not count outages as wrong passwords. Each firing site is responsible for keeping that line. `signInBody` shows it (shortened):

```go
user, err := ac.Store.FindUserByEmail(hctx.Ctx, creds.Email)
if err != nil {
	if behemotherr.IsNotFound(err) {
		dispatcher.Fail(hctx, hooks.HookSignInFailed, types.FailureReason{Code: "userNotFound"})
		return nil, errors.New("invalid email or password")
	}
	return nil, err // not a rejection: no Fail
}
```

# **Design decisions**

### Hooks get their own context type
**Context:** Route handlers already receive a `RequestContext`. Hook handlers need much of the same (a context, the `AuthContext`, a scratch map).
**Options considered:**
- *Reuse `RequestContext`.* One type to learn. Every firing site without a request would have to build an empty one, and handlers would need nil checks on `Request.Header` and the response recorder in code that has nothing to do with HTTP.
- *A separate `HookContext` with the request as an optional field.* A second type. Firing sites below the HTTP layer build it from what they have, and the nil `Request` states plainly that there is none.
**Decision:** The separate type. It also gives a place for fields a request context has no use for: `Point`, `Phase` and `Tx`.

### The request travels in the `context.Context`
**Context:** A data hook should be able to see the request that caused the write (IP address, headers), but the store's API takes a `context.Context` and `store` can't import `types`.
**Options considered:**
- *Add a request parameter to the store's write methods.* Explicit. It puts an HTTP type in the data layer's signatures, which the import direction forbids, and every caller without a request passes nil.
- *Carry the request in the context.* The store's API is untouched. A context value is implicit: nothing in a signature shows that it is expected, and a caller that passes a fresh context loses it.
**Decision:** The context, for the request only. The request is request-scoped by definition, which is what context values are for. Other dependencies stay explicit, in line with the repository rule to prefer visible parameters.
**Revisit if:** more values are proposed for the same route. Each one makes the implicit contract wider. The operation's `Values` were added later, see "The operation's values travel in the context" below.

### The session manager takes the IP address and user agent from the request
**Context:** `SessionManager.Create` received both in `SessionMeta`, and each caller extracted them. The email/password sign-in read `hctx.Request.Request.RemoteAddr` without a nil check, so it panicked outside a request, and behind a proxy it stored the proxy's address.
**Options considered:**
- *Keep the extraction in each caller.* Explicit. Every sign-in method (OAuth, magic link, a second factor) repeats it and has to get the nil check and the proxy rule right.
- *A helper the caller invokes*, for example `SessionMetaFrom(rctx)`. Still explicit, and the rules live in one function. A new caller can forget it, and nothing reports a session without an address.
- *The manager reads the request from the context, with `SessionMeta` as an override.* One place for the rules, next to `CaptureIPAndAgent`, and the `Create` signature stays. The dependency is implicit: a caller that passes a fresh context gets a session without an address.
**Decision:** The manager reads it. The request is the one value that already travels in the context, and the manager already reads it there for its hook contexts. The `SessionMeta` fields stay for a caller without a request that knows the values.
**Revisit if:** sessions without an address turn up from callers that dropped the context. A warning log in `Create` when capture is on and no request is found would be the first step.

### A nil payload from a before handler means "no change"
**Context:** `RunBefore` passed on whatever a handler returned. A `nil, nil` from one handler made the next handler's first write panic. From the last or only handler the nil reached the firing site: `Store.create` read it into the model with `FromMap`, which blanks every field, and `Store.update` wrote `updated_at` into it and panicked outside the dispatcher's recover.
**Options considered:**
- *Leave it and document the rule.* No code. A handler that only validates is the common case, and `return nil, nil` is the natural way to write one, so the cases above stay reachable.
- *Treat nil as an error.* `RunBefore` stops with an internal error naming the handler. The mistake is found at the handler that made it. Every validator has to return the payload, and one that forgets fails each request through the point. On the veto-only points the returned payload is not even read.
- *Treat nil as "no change".* `RunBefore` keeps the payload it had. No nil reaches a handler or a firing site. A handler that built a new map and returned nil by mistake loses its rewrite without a trace.

**Decision:** "No change". It removes the nil instead of reporting it, and the mistake it hides is of the same kind as returning the original `payload` after building a new one, which no check catches either. `RunBefore` also turns a nil input into an empty map, so the rule holds for a firing site that passes nil.
**Revisit if:** lost rewrites show up in practice. A debug log line when a handler returns nil would be the first step.

### Three before points are veto-only
**Context:** `auth.session.beforeRevoke`, `token.beforeIssue` and `auth.signOut.before` drop the returned payload. Their payloads hold a session id and reason, a token kind and subject.
**Options considered:**
- *Read the payload back.* Uniform with the other points. A handler could then revoke a session other than the one the caller named, or issue a token for another subject or of another kind (the kind selects the backend and the TTL).
- *Read back only the harmless keys.* That leaves `reason` on revoke. Nothing asks for it.
- *Keep them veto-only.* The firing site's values stand. The API docs mark the points.

**Decision:** Veto-only. The keys identify what the operation acts on, and that stays the caller's decision.
**Revisit if:** a handler needs to shape a token, to shorten its lifetime for example. Add a key for that value to the payload (`expiresAt`) and read back that key only.

### `auth.session.beforeCreate` reads back the IP address and user agent
**Context:** The site read back the user agent only, under a comment that named both. A handler's IP address had no effect. With `CaptureIPAndAgent` off, a handler could still set a user agent that the config said not to store.
**Options considered:**
- *Fix the comment and read the user agent only.* The smallest change. The IP address stays in the payload as a key that looks writable and isn't.
- *Read both back, always.* Masking or truncating the address before it is stored works. A handler can turn capture back on for a deployment that turned it off.
- *Read both back when capture is on.* The same, and the config stays the last word.

**Decision:** Both, when capture is on. `HookValueUserID` and `HookValueState` are left out on purpose: a handler that changed the state from pending to active would skip the second factor.

### `Values` last for one operation
**Context:** `Values` was documented as scoped to one chain, and the managers and `dataHooks` built a fresh map per dispatch. The email/password flows reused one context, so there a note lasted from the before point to the after point. An after handler receives the result and not the input, so a handler that resolves something from the input (an invite id, a consent flag, a risk score) needs a way to hand it to the after or failed point.
**Options considered:**
- *One chain everywhere.* Matches the old comment. The invite case then needs `Request.Values`, which is missing when a flow runs from a job, or a second lookup in the after handler.
- *Whatever the firing site does.* No code change. The same handler behaves differently depending on who fires the point.
- *One operation: the before, after and failed points of one call share a map.* The managers and `dataHooks` need a way to tie their dispatches together. Handlers get one rule for every point.
**Decision:** One operation. `forPoint` in the dispatcher sets `Point` and `Phase` on a copy that shares the map, so a flow can use one context for all its points.
**Revisit if:** operations start running handlers concurrently. The shared map would then need a lock or a per-goroutine copy.

### A nested operation gets a copy of the outer values
**Context:** The user write inside a sign-up is the place to add rows atomically with the user. Its handlers need what the flow's handlers resolved.
**Options considered:**
- *Nested operations start empty.* Simple. The invite link can then only be made after commit, in `auth.signUp.after`, with a claim-and-release scheme to stay correct.
- *Nested operations share the outer map.* One map for the whole call tree. Unrelated handlers in different operations write to it, a key collision is silent, and `dataHooks` writing the row id for update points would land in the flow's map.
- *A map with a fallback to the outer one.* Reads see the outer values and writes stay local. `Values` could no longer be a plain map; every handler would change to `Get` and `Set`.
- *A copy of the outer map at the start.* Same reads and local writes, with a plain map. A value the outer operation writes after the inner one started is not seen, which can't happen while operations run in sequence.
**Decision:** The copy. It costs one small map per nested operation and keeps `Values` a `behemoth.M`.
**Revisit if:** an inner operation has to hand something back to the outer one. Today it can only do that through the result.

### The operation's values travel in the context
**Context:** The data hooks of a write and the points of a manager have to find the operation they are nested in. Between the flow and those sites are `Store` and manager methods that take a `context.Context`.
**Options considered:**
- *A store bound to the operation* (`ac.Store.WithScope(hctx)`). Explicit at the call site, and `store.Hooks` already receives the store. It covers the store only; every manager method would need a parameter as well. A flow body that uses `ac.Store` directly loses the link, and so does any helper in between.
- *A parameter on every store and manager method.* The most explicit and the most invasive.
- *The context.* No signature changes, and it reaches any depth, including another plugin's function called from the flow. It is implicit: a callee handed a fresh context starts with empty values and nothing reports it.
**Decision:** The context, set by `WithLifecycle` (`AsOperation`) and `BeginOperation`, so flow bodies need no code for it. It is an exception to the repository rule of preferring visible parameters, made for the same reason as the request: the value is scoped to the call, and the code in between should not know about hooks.
**Revisit if:** lost links become a source of bugs. A scoped store could be added next to the context for the store path.
