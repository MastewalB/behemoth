## **Hook Declaration and Priority**

This document explains the startup half of the hook system: how points are declared into the `HookCatalog`, how handlers are attached through the `HookRegistry`, how owner names are stamped on both, and how the handlers of each point are put in a fixed order before the first request.

All code referenced here is in `types/init/init.go` unless a file is named.

---

# **Two phases**

A plugin takes part in two separate passes over the plugin list:

| Pass | Runs in | Plugin method | Works on |
| --- | --- | --- | --- |
| Declaration | `Prepare` | `Declare(ic *PluginInitContext)` | `ic.Hooks`, a `HookCatalog` |
| Registration | `Boot` | `Register(reg HookRegistry)` | a `HookRegistry` |

Every plugin has declared before any plugin registers. A plugin can therefore register a handler on a point that a plugin later in the list declares. If declaring and registering were one step, plugin B could only hook plugin A's points when A happened to run first.

The split also follows the line between `Prepare` and `Boot`. `Prepare` needs no database and no secrets, so migration tooling can call it alone. Declaring a point is pure data and belongs there. A handler is a closure over a running application and belongs to `Boot`.

Both passes visit plugins in the order `ResolvePluginOrder` returns: a topological order of `PluginMeta.Dependencies`, with ties broken by plugin name. The same order is used later to break ties between handlers.

# **Declaration**

### **`HookPointDef`**

```go
type HookPointDef struct {
	Point HookPoint
	Owner string
	Phase HookPhase
	Audit *AuditSpec
}
```

| Field | Set by | Meaning |
| --- | --- | --- |
| `Point` | the declarer | the name |
| `Owner` | the scoped catalog; whatever the declarer wrote is overwritten | who declared it |
| `Phase` | the declarer | the point's one phase |
| `Audit` | the declarer, optional | when set, each dispatch records an audit event after the chain: best effort for `RunAfter` and `Fail`, in the write's transaction for `RunAfterTx`. `AuditSpec.Type` defaults to the point name. |

### **`HookCatalog`**

```go
type HookCatalog interface {
	Declare(def HookPointDef) error
	Lookup(point HookPoint) (HookPointDef, bool)
	All() []HookPointDef
}
```

`DefaultHookCatalog` is the one implementation: a map from point to definition, a read-write lock, and a `frozen` flag.

`Declare` rejects, in this order:

| Condition | Message |
| --- | --- |
| the catalog is frozen | `cannot Declare after boot has completed` |
| `Point` is empty | `HookPointDef.Point must not be empty` |
| `Owner` is empty | `point "x" missing Owner` |
| `Phase` is not one of the three | `point "x" declared with invalid or missing Phase "..."` |
| the point is already declared | `point "x" already declared by "a", cannot redeclare from "b"` |

Each is a `ConfigurationError`. A declaration is first come, first served: a second declaration of a name fails even when the same owner makes it.

`Lookup` is used by the registry, the rate-limit catalog, `checkDataHookPoints` and the dispatcher. `All` is used by `freezeAllHookChains`, which needs every declared point, including those without handlers.

`Freeze` is a method of `DefaultHookCatalog` and not of the interface, so a plugin holding a `HookCatalog` can't call it. `Prepare` calls it once every declarer has run.

### **Owner scoping: `scopedHookCatalog`**

A plugin never receives the `DefaultHookCatalog`. `Prepare` builds a `PluginInitContext` per declarer with `newScopedInitContext`, whose `Hooks` field is:

```go
type scopedHookCatalog struct {
	inner types.HookCatalog
	owner string
}

func (s *scopedHookCatalog) Declare(def types.HookPointDef) error {
	def.Owner = s.owner
	return s.inner.Declare(def)
}
```

A plugin can't declare a point in another owner's name, and it does not have to fill in `Owner`. `Lookup` and `All` pass through, so a plugin can see what earlier declarers added.

The token catalog, the rate-limit catalog and the schema registry are wrapped the same way.

### **The order of declaration in `Prepare`**

1. `DetectPluginNameConflicts` and `checkOwnerNames`: no two plugins share a name, no plugin is called `core` or the application's name, and the application is not called `core`. Owner names attribute points and order handlers, so each has to mean one thing.
2. `ResolvePluginOrder`.
3. The catalogs are created. The rate-limit catalog gets a reference to the hook catalog.
4. Core declares, through a context scoped to `core`: `CoreDeclareHookPoints`, then `CoreDeclareRateLimitRules`, then `CoreDeclareSchema`.
5. Each plugin's `Declare` runs, through a context scoped to its name.
6. The application's `PrepareConfig.Schema` runs. It gets a schema registry only. The application can't declare hook points.
7. `hookCatalog.Freeze()`, and the same for the other catalogs.

Core declares first, so no plugin can take one of core's names.

Hook points come before rate-limit rules in step 4 for a reason: `DeclareHookRateLimitRule` looks the rule's point up in the hook catalog and rejects a rule on an undeclared point or on a point that is not a before point. A plugin that declares a point and a rule on it in the same `Declare` has to declare the point first.

`Prepare` returns the frozen catalog as `PreparedApp.Hooks`.

# **Registration**

### **`HookRegistry` and `HookOptions`**

```go
type HookRegistry interface {
	OnBefore(point HookPoint, fn BeforeHookFunc, opts *HookOptions) error
	OnAfter(point HookPoint, fn AfterHookFunc, opts *HookOptions) error
	OnFailed(point HookPoint, fn FailedHookFunc, opts *HookOptions) error
}

type HookOptions struct {
	Priority HookPriority
	Before   []string
	After    []string
}
```

There is one method per phase, so the function type is checked by the compiler: a `BeforeHookFunc` can't be passed to `OnAfter`.

`opts` may be nil, which means `PriorityNormal` and no constraints. `Before` and `After` name owners (plugin names, or the application's name), not handlers.

```go
const (
	PriorityHighest HookPriority = -100
	PriorityHigh    HookPriority = -50
	PriorityNormal  HookPriority = 0
	PriorityLow     HookPriority = 50
	PriorityLowest  HookPriority = 100
)
```

A lower number runs earlier. `HookPriority` is an `int`, and any value is accepted, not just the five constants.

### **`DefaultHookRegistry`**

```go
type DefaultHookRegistry struct {
	mu      sync.Mutex
	catalog types.HookCatalog
	pending map[types.HookPoint][]registeredHandler
	frozen  bool
}

type registeredHandler struct {
	plugin   string
	priority types.HookPriority
	before   []string
	after    []string
	handler  any
}
```

All three interface methods end in `register(point, phase, owner, fn, opts)`. It rejects, in this order:

| Condition | Message |
| --- | --- |
| the registry is frozen | `cannot register after chains have been frozen` |
| the point is not in the catalog | `point "x" was never declared` |
| the point's phase differs from the method's | `point "x" is phase "after", cannot register a "before" handler on it` |
| this owner already has a handler on the point | `"p" already registered a handler on point "x"; an owner may register one handler per point` |

Otherwise it appends a `registeredHandler` to `pending[point]`. The list is in registration order and has no meaning yet.

The second check is what makes a typo a startup failure. A plugin that registers on `toltp.beforeVerify` fails `Boot` with the point's name in the message. Without the catalog it would register a handler that never runs.

`handler` is stored as `any`. The phase check above guarantees that a before point only ever holds `BeforeHookFunc`s, so the type assertion the dispatcher makes later can't fail.

### **Owner scoping: `scopedHookRegistry`**

As with the catalog, a plugin gets a wrapper:

```go
type scopedHookRegistry struct {
	inner *DefaultHookRegistry
	owner string
}

func (s *scopedHookRegistry) OnBefore(point types.HookPoint, fn types.BeforeHookFunc, opts *types.HookOptions) error {
	return s.inner.register(point, types.BeforeHookPhase, s.owner, fn, opts)
}
```

The owner comes from `Boot`, not from the plugin, so a handler is always attributed to the plugin whose `Register` added it. Ordering depends on that name.

`DefaultHookRegistry` itself does not implement `types.HookRegistry`. Its only way in is the unexported `register`, which takes the owner, so a handler can't be registered without one.

### **The order of registration in `Boot`**

1. `NewHookRegistry(app.Hooks)`.
2. Each plugin's `Register` runs with `&scopedHookRegistry{inner: hookRegistry, owner: name}`, in plugin order.
3. If `BootConfig.Hooks` is set, it runs with a registry scoped to `app.AppName`, and the application's name is appended to the order used for tie-breaking.
4. `freezeAllHookChains(app.Hooks, hookRegistry, hookOrder)`.

Core registers no handlers. It declares points and fires them.

The application registers through the same registry as a plugin and is treated as the last plugin: the same checks apply, including one handler per point, and other owners can name it in `Before` and `After`. `PrepareConfig.AppName` sets its name, `app` by default.

# **Order resolution**

`freezeAllHookChains` walks `catalog.All()` and calls `resolvePointOrder` for each point's pending handlers. The result is `map[HookPoint][]registeredHandler` with an entry for every declared point. It then sets `registry.frozen`, and later `register` calls fail.

A point with no handler or one handler is returned as it is. For two or more, the order is decided in three layers.

### **Layer 1: priority buckets**

Handlers are grouped by `priority`. The buckets are sorted by ascending number and concatenated, so every `PriorityHighest` handler runs before every `PriorityHigh` handler.

The intended use is by role:

- **early buckets** for gatekeepers that should see the raw input: validation, security checks
- **late buckets** for observers that should see the final state: logging, analytics

### **Layer 2: `Before` and `After` within a bucket**

Inside a bucket with two or more handlers, `topoSortBucket` builds a graph with one node per owner:

- `h.before = ["x"]` adds the edge `h → x`
- `h.after = ["x"]` adds the edge `x → h`

An edge is only added when `x` has a handler in the same bucket of the same point. The graph is sorted with `types.KahnSort`.

A constraint that names an owner outside the bucket falls into one of three cases:

| The named owner | Result |
| --- | --- |
| has no handler on this point | ignored. This is how an optional integration works: "after `totp`, if it is installed". |
| is in another bucket, and the bucket order already satisfies the constraint | ignored as redundant |
| is in another bucket, and the bucket order contradicts the constraint | `Boot` fails |

The contradiction check runs for every handler before its bucket is sorted. With `p` the handler's own priority:

```go
for _, mustBeBefore := range h.before {
	if otherP, ok := priorityOf[mustBeBefore]; ok && otherP < p {
		// "x" wants to run before "y", but "y" sits in a higher-priority bucket
	}
}
for _, mustBeAfter := range h.after {
	if otherP, ok := priorityOf[mustBeAfter]; ok && otherP > p {
		// "x" wants to run after "y", but "y" sits in a lower-priority bucket
	}
}
```

A handler at `PriorityLow` that asks to run before a handler at `PriorityHighest` is asking for two things that can't both hold. Reporting it is better than letting whichever mechanism ran last win.

A cycle inside a bucket (`a` before `b`, `b` before `a`) also fails `Boot`: `point "x": circular handler ordering: a -> b -> a`.

### **Layer 3: plugin boot order**

Where the graph leaves two handlers unordered, `KahnSort` picks by a comparator. For handlers it is the position of the owner in the boot order:

```go
indexOf := make(map[string]int, len(pluginOrder))
for i, name := range pluginOrder {
	indexOf[name] = i
}
registrationOrder := func(a, b string) bool { return indexOf[a] < indexOf[b] }
```

`pluginOrder` is the resolved plugin order with the application's name appended. So among unconstrained handlers of equal priority, a plugin runs after the plugins it depends on, and the application runs last.

The comparator decides between handlers that are ready at the same step of the sort. It is not a global sort by boot order: a constraint can hold an early plugin back, as `geo` in the example below.

The result is deterministic. It does not depend on map iteration or on the order `Register` calls were made in.

### **A worked example**

Plugins boot in the order `geo`, `lockout`, `totp`. The application is `app`. Four handlers are registered on `auth.signIn.credentialsVerified`:

| Owner | Priority | Constraint |
| --- | --- | --- |
| `geo` | `PriorityNormal` | `After: ["totp"]` |
| `lockout` | `PriorityHighest` | |
| `totp` | `PriorityNormal` | `After: ["sms"]` |
| `app` | `PriorityNormal` | |

1. Buckets: `-100: [lockout]`, `0: [geo, totp, app]`.
2. Contradiction check: `geo` after `totp` is inside one bucket, so it is left to the graph. `totp` after `sms`: `sms` has no handler here, ignored.
3. Bucket `-100` has one handler: `lockout`.
4. Bucket `0`: the graph has the edge `totp → geo`. Ready at the start are `totp` and `app`. By boot order `totp` (index 2) comes before `app` (index 3). Taking `totp` frees `geo` (index 0), which now sorts before `app`.

The chain is `lockout`, `totp`, `geo`, `app`.

### **Errors from this stage**

All are `ConfigurationError`s with the operation `HookRegistry.Freeze`, returned from `Boot`:

- a `Before` or `After` that contradicts the bucket order
- a cycle within a bucket

### **The output**

```go
frozenChains map[types.HookPoint][]registeredHandler
```

One slice per declared point, in the order the handlers will run. `Boot` passes it to the `DefaultDispatcher`. The registry is not used again.

A point with no handlers has an entry with a nil slice. The dispatcher ranges over it and runs nothing, so "declared, no handlers" and "has handlers" take the same path. A point missing from the catalog is a different case and is rejected before the chains are read (`checkPhase`).

# **What is checked when**

| Mistake | Caught by | When |
| --- | --- | --- |
| two plugins with one name; a plugin named `core` or like the application | `DetectPluginNameConflicts`, `checkOwnerNames` | `Prepare` |
| empty point name, invalid phase | `DefaultHookCatalog.Declare` | `Prepare` |
| a point declared twice | `DefaultHookCatalog.Declare` | `Prepare` |
| a rate-limit rule on an undeclared or non-before point | `DeclareHookRateLimitRule` | `Prepare` |
| a handler on an undeclared point | `DefaultHookRegistry.register` | `Boot` |
| a handler of the wrong phase | the compiler for the function type, `register` for the point | build, `Boot` |
| two handlers from one owner on a point | `register` | `Boot` |
| contradictory or circular ordering | `resolvePointOrder`, `topoSortBucket` | `Boot` |
| a store table mapped to an undeclared point | `checkDataHookPoints` | `Boot` |
| firing an undeclared point, or in the wrong phase | `DefaultDispatcher.checkPhase` | request time |

The last row is the only one that is not caught at startup. See [5. Hook Dispatching](<5. Hook Dispatching.md>).

# **Design decisions**

### Declaration and registration are separate passes
**Context:** A plugin may hook a point that another plugin declares. With a single initialization step, that works only when the declaring plugin runs first.
**Options considered:**
- *One step, ordered by plugin dependencies.* Simple. A plugin must then list every plugin whose points it hooks as a dependency, including optional integrations, and two plugins hooking each other's points can't be ordered at all.
- *Two passes: all declarations, then all registrations.* Each plugin implements two methods. Any plugin can hook any declared point, whatever the order.
**Decision:** Two passes. They also match the `Prepare` and `Boot` split, which keeps declarations available to tooling that never boots the application.

### An owner registers one handler per point
**Context:** Order is resolved by owner name: `Before` and `After` name owners, the topological sort has one node per owner, and ties are broken by the owner's position in the boot order. Two handlers from one owner on one point can't be told apart by any of these. In the sort they would collapse into one node and one of them would be lost.
**Options considered:**
- *Allow several and add a sequence number as a last tie-break.* Keeps plugins free to split work. `Before: ["x"]` would then mean "before all of x's handlers", the graph needs a node per handler, and the result depends on the order of calls inside `Register`.
- *Reject the second registration.* A plugin with two steps on a point writes one handler that calls both. Names keep identifying exactly one handler per point.
**Decision:** Reject it, with an error naming the owner and the point. A different priority does not make a second slot.
**Revisit if:** plugins commonly need two handlers on a point in different priority buckets, for example a gatekeeper and an observer on the same before point.

### Ties are broken by plugin boot order
**Context:** Two handlers of equal priority with no constraint between them need a fixed order.
**Options considered:**
- *Registration order.* Depends on the order of calls, which follows boot order across plugins anyway but is harder to state.
- *Alphabetical by owner.* Stable, but unrelated to anything a plugin author controls short of renaming the plugin.
- *The owner's position in the resolved plugin order, application last.* Stable, and a declared dependency gives the expected result: a plugin's handler runs after the handlers of the plugins it depends on.
**Decision:** Boot order. It needs no option on the handler, and the application running last suits its usual role of adjusting what plugins did.

### Priorities and constraints may not contradict
**Context:** Priority buckets and `Before`/`After` both express order. A handler can name an owner whose handler is in another bucket.
**Options considered:**
- *Let one mechanism override the other.* No startup error. One of the two requests is dropped without notice.
- *Ignore agreeing constraints, reject contradicting ones.* A plugin author learns at startup that the requested order can't be produced.
**Decision:** Reject contradictions at `Boot`, naming the point and both owners. A constraint that names an owner with no handler on the point is still ignored, so optional integrations need no check on the caller's side.
