## **Data Hooks**

This document explains how a write through the store becomes a hook dispatch. It covers the `store.Hooks` interface the store calls, the `dataHooks` adapter in `types/init/datahooks.go` that implements it on top of the `Dispatcher`, the table that maps a store table to its points, and the steps to give another table data hooks.

The transaction side (what `HookContext.Tx` is bound to, what a rollback undoes, how the commit queue works, the limits on MongoDB and SQLite) is described in [`../models/models.md`](../models/models.md#data-hooks-and-transactions). This document stays on the path from the store to the handler and repeats only what is needed to follow it.

---

# **Two interfaces, one adapter**

The store and the dispatcher don't know each other. Each side has an interface in its own terms, and `dataHooks` translates.

| | `store.Hooks` | `types.Dispatcher` |
| --- | --- | --- |
| Defined in | `store/store.go` | `types/plugins.go` |
| Called by | `Store.hooked`, `Store.create`, `Store.update` | firing sites |
| Speaks of | a table name, a row (`behemoth.M`), a model | a hook point, a `HookContext`, a payload or result |
| Implemented by | `dataHooks`, `noHooks` | `DefaultDispatcher` |

`store` can't import `types`, because `types` imports `store`. The store therefore states what it needs as `store.Hooks`, and `Boot` supplies the implementation with `store.WithHooks`. See [1. Purpose and Components](<1. Purpose and Components.md>) for the import table.

```
Store.hooked ──► store.Hooks.Begin(ctx, "users")            →  the write's context
Store.create ──► store.Hooks.BeforeCreate(ctx, tx, "users", row)
                        │
                        ▼  dataHooks
                 coreDataHookPoints["users"].beforeCreate  →  data.user.beforeCreate
                 hookContext(ctx, tx, point, phase)        →  *types.HookContext
                        │
                        ▼
                 Dispatcher.RunBefore(hctx, point, row)
                        │
                        ▼
                 the handlers registered on data.user.beforeCreate
```

# **`store.Hooks`**

```go
type Hooks interface {
	Fires(table string) bool
	Begin(ctx context.Context, table string) context.Context

	BeforeCreate(ctx context.Context, tx *Store, table string, row behemoth.M) (behemoth.M, error)
	AfterCreate(ctx context.Context, tx *Store, table string, created behemoth.Model) error

	BeforeUpdate(ctx context.Context, tx *Store, table string, id any, changes behemoth.M) (behemoth.M, error)
	AfterUpdate(ctx context.Context, tx *Store, table string, updated behemoth.Model) error
}
```

| Method | Called | May | Its error |
| --- | --- | --- | --- |
| `Fires` | before a write, to decide whether to open a transaction | | |
| `Begin` | once per hooked write, in the transaction, before the before call | return the context the rest of the write runs with | |
| `BeforeCreate` | in the transaction, before the insert | rewrite the row | aborts the create |
| `AfterCreate` | in the transaction, after the insert | write through `tx`, queue a callback with `tx.AfterCommit` | rolls the create back |
| `BeforeUpdate` | in the transaction, before the update | rewrite the changes | aborts the update |
| `AfterUpdate` | in the transaction, after the update and read-back | write through `tx`, queue a callback with `tx.AfterCommit` | rolls the update back |

Points about the shape:

- **`tx` is the store itself**, bound to the transaction. The store passes it so the implementation can hand it to handlers and queue work on its commit.
- **`table` is the model's `SchemaName()`.** The store has no other name for what it writes.
- **`id` is a separate argument of `BeforeUpdate`** and not a key in `changes`. A hook can't redirect an update to another row by rewriting the map.
- **`Begin` ties the calls of one write together.** The store does not know what the returned context carries. It passes it to the write and to the write's before and after calls. The context has to be derived from the one `Begin` received, because on MongoDB that one carries the transaction.
- **There is no "committed" call.** The store offers `AfterCommit`, and an implementation that wants to act once the write is durable queues a callback from its after method. The store itself knows nothing about committed notifications.

### **`noHooks`**

`store.New` starts with `noHooks{}`: `Fires` returns false, `Begin` and the before methods return their input, the rest do nothing. A store built without `WithHooks` fires no data hooks and opens no transaction of its own. Two stores are built that way on purpose:

- the rate limiter's counter store in `Boot`
- stores in tests that are not about hooks

# **The store side**

The write paths are in `store/create.go`. Each public method (`CreateUser`, `UpdateUser`, ...) sets up its model and calls `create` or `update`.

### **`hooked`: transaction or not**

```go
func (s *Store) hooked(ctx context.Context, table string, write func(ctx context.Context, tx *Store) error) error {
	if !s.hooks.Fires(table) {
		return write(ctx, s)
	}
	return s.Transaction(ctx, func(ctx context.Context, tx *Store) error {
		return write(tx.hooks.Begin(ctx, table), tx)
	})
}
```

A table that fires hooks gets its write and its hooks in one transaction. `Store.Transaction` joins the transaction the store is already bound to, or opens one. `Begin` runs inside it, once per write, and on MongoDB again for each retry of the transaction. A table that fires none writes directly through `s`.

`Fires` is the gate for the cost. Without it every session and token write would open a transaction, and the rate limiter's counter store could not stay outside one.

### **A create**

`Store.create(ctx, m, prepare)`, as called by `CreateUser` after it has set the id, the timestamps and the normalized email:

| Step | Code | On error |
| --- | --- | --- |
| 1 | `row := m.ToMap()` | returned |
| 2 | `row = hooks.BeforeCreate(ctx, tx, table, row)` | returned as it is: the handler's veto |
| 3 | `checkColumns(m, row)`: every key is a column of the table | validation error |
| 4 | `prepare(row)`: for users, normalizes the email | |
| 5 | `m.FromMap(row)`: the rewrite is read back into the model | validation error |
| 6 | `tx.db.Create(ctx, m)` | returned |
| 7 | `hooks.AfterCreate(ctx, tx, table, m)` | returned as it is; the insert is rolled back |

Step 3 exists because `FromMap` ignores keys the model does not have. Without the check a handler could set a column that does not exist and believe it was stored.

The model has to implement `behemoth.Serializable`, since hooks work on rows.

### **An update**

`Store.update(ctx, m, id, changes, stamp, prepare)`, as called by `UpdateUser`:

| Step | Code | On error |
| --- | --- | --- |
| 0 | `checkUpdate(m, changes)`: no primary key, only known columns | validation error, before any transaction |
| 1 | `changes = hooks.BeforeUpdate(ctx, tx, table, id, copyRow(changes))` | returned as it is |
| 2 | `checkUpdate(m, changes)` again, on the handlers' version | validation error |
| 3 | `prepare(changes)`: for users, normalizes the email | |
| 4 | `changes[stamp] = now` (`updated_at`) | |
| 5 | `tx.db.UpdateOne`, then `tx.db.FindOne` to read the stored row | returned |
| 6 | `hooks.AfterUpdate(ctx, tx, table, updated)` | returned as it is; the update is rolled back |

- Handlers get a copy of the caller's map. The caller's map is never changed.
- Normalization and the timestamp are applied after the handlers, so a value a handler set is normalized too, and a handler can't set `updated_at`.
- The after hook gets the whole stored row, not the change set.

Create normalizes twice. `CreateUser` does it before `create` runs, so `beforeCreate` handlers see the stored form, and `prepare` does it again on the row the handlers returned. Both paths use `normalizeUserRow`. The id and the timestamps are set before the handlers on create and are not reapplied, so a `beforeCreate` handler can rewrite them.

### **After the commit**

The store has one tool for work that should wait for the commit, and it is not specific to hooks:

```go
func (s *Store) AfterCommit(ctx context.Context, fn func(ctx context.Context))
```

On a store bound to a transaction it appends `fn` to that transaction's queue. `Store.Transaction` runs the queue once the adapter's transaction has returned without an error, and drops it otherwise. A write that joined a caller's transaction shares that transaction's queue, so a callback waits for the outermost commit. On a store that is not bound to a transaction `fn` runs at once. A panic in `fn` is recovered and logged in both cases, and the callbacks queued behind it still run. The full description is in [`../models/models.md`](../models/models.md#data-hooks-and-transactions).

`dataHooks` uses it from its after methods to fire the `created` and `updated` points (below).

# **The adapter: `dataHooks`**

```go
type dataHooks struct {
	ac     *types.AuthContext
	points map[string]tableHookPoints
}
```

It holds the `AuthContext`, for the dispatcher and to put on each `HookContext`, and the table-to-points map.

### **`tableHookPoints` and `coreDataHookPoints`**

```go
type tableHookPoints struct {
	beforeCreate, afterCreate types.HookPoint
	beforeUpdate, afterUpdate types.HookPoint
	created, updated          types.HookPoint
	idValue                   string
}

var coreDataHookPoints = map[string]tableHookPoints{
	"users": {
		beforeCreate: hooks.HookUserBeforeCreate, afterCreate: hooks.HookUserAfterCreate,
		beforeUpdate: hooks.HookUserBeforeUpdate, afterUpdate: hooks.HookUserAfterUpdate,
		created: hooks.HookUserCreated, updated: hooks.HookUserUpdated,
		idValue: hooks.HookValueUserID,
	},
}
```

The map is the whole definition of Tier 1. A table with an entry fires its six points and writes in a transaction. A table without one fires nothing. `users` is the only entry.

`idValue` is the `HookContext.Values` key under which the row's id is published for update points.

### **Method by method**

| `store.Hooks` method | Point | Dispatcher call | `Tx` | `Values[idValue]` |
| --- | --- | --- | --- | --- |
| `Fires(table)` | | none: a map lookup | | |
| `Begin` | | none: opens the write's operation | | |
| `BeforeCreate` | `beforeCreate` | `RunBefore(hctx, point, row)` | set | |
| `AfterCreate` | `afterCreate` | `RunAfterTx(hctx, point, created)` | set | |
| `AfterCreate`, queued for the commit | `created` | `RunAfter(hctx, point, created)` | nil | |
| `BeforeUpdate` | `beforeUpdate` | `RunBefore(hctx, point, changes)` | set | the `id` argument |
| `AfterUpdate` | `afterUpdate` | `RunAfterTx(hctx, point, updated)` | set | `updated.PrimaryKeyField()` |
| `AfterUpdate`, queued for the commit | `updated` | `RunAfter(hctx, point, updated)` | nil | inherited from the write |

Each method first looks the table up in `points`. For an unmapped table the before methods return their input and the others return at once. The store has already asked `Fires`, so this branch is a safeguard.

The returned values go straight back to the store. `BeforeCreate` returns what `RunBefore` returned: the rewritten row, or the handler's error, a rate-limit error or a configuration error. `AfterCreate` returns `RunAfterTx`'s error. The adapter adds and wraps nothing, which is why a handler's error reaches the caller of `Store.CreateUser` with its type intact.

### **One write, one operation: `Begin`**

```go
func (h dataHooks) Begin(ctx context.Context, table string) context.Context {
	if _, ok := h.points[table]; !ok {
		return ctx
	}
	return types.BeginOperation(ctx)
}
```

`BeginOperation` puts a new `Values` map on the context: a copy of the enclosing operation's, or an empty map when the write is not inside one. Every dispatch of the write reads that map from its context, so `beforeCreate`, `afterCreate` and `created` share it, and a write inside a sign-up sees what the sign-up's handlers left. What the write's handlers add stays in the copy. The rule and its reasons are in [3. Hook Context](<3. Hook Context.md>).

On a retried MongoDB transaction the store calls `Begin` again, so each attempt starts from the enclosing values and not from a previous attempt's notes.

### **The committed points**

`AfterCreate` and `AfterUpdate` end with `onCommit`, once the in-transaction chain has succeeded:

```go
func (h dataHooks) onCommit(ctx context.Context, tx *store.Store, values behemoth.M, point types.HookPoint, row behemoth.Model) {
	tx.AfterCommit(ctx, func(ctx context.Context) {
		hctx := h.hookContext(types.ContextWithHookValues(ctx, values), nil, point, types.AfterHookPhase)
		if err := h.ac.Dispatcher.RunAfter(hctx, point, row); err != nil && h.ac.Telemetry.Logger != nil {
			h.ac.Telemetry.Logger.Error(hctx.Ctx, "after-commit data hook could not be dispatched", ...)
		}
	})
}
```

- **Queued only on success.** When the after chain returns an error, `onCommit` is not reached and nothing is queued.
- **Two contexts.** The callback runs with the context `Store.Transaction` was called with. The write's own context is the transaction's and is no longer usable (on MongoDB it carries the ended session). The write's `Values` are captured before and put on the callback's context, so the committed point keeps the write's notes, and an operation a handler starts from it nests under the write.
- **The error.** `RunAfter` only returns an error when the point can't be dispatched, and `checkDataHookPoints` has ruled that out at `Boot`. The callback has nobody to return it to, so it is logged.

Because these go through `RunAfter`, they behave like Tier 2 after points: handler errors are logged, every handler runs, and an audit event is recorded when the point declares one.

### **The context**

`dataHooks.hookContext(ctx, tx, point, phase)` builds a `HookContext` per dispatch: the point and phase, the `AuthContext`, `tx` as `Tx`, the write's `Values` (`types.HookValuesFrom(ctx)`), and the request taken from the context with `types.RequestFrom`. See [3. Hook Context](<3. Hook Context.md>).

`ctx` is the context `Begin` returned. Inside a transaction it is derived from the transaction callback's context, which is the one a handler has to pass to `hctx.Tx` and `hctx.Tx.DB()`.

### **The boot check: `checkDataHookPoints`**

The map names points by constant, and nothing in the type system ties an entry to a declaration. `Boot` checks each of the six points of every entry against the catalog:

| Problem | Error |
| --- | --- |
| the point is not declared | `data hook point "x" of table "t" was never declared` |
| the point is declared with another phase than the store fires it in | `data hook point "x" of table "t" is declared as phase "before", the store fires it as "after"` |

Without the check, the mistake would surface as a configuration error on the first write to the table.

# **One `CreateUser`, traced**

`ac.Store.CreateUser(ctx, u)` called on the root store, with one handler on each of the three create points:

1. `CreateUser` sets `u.ID`, the timestamps and the normalized email, and calls `create`.
2. `hooked` asks `dataHooks.Fires("users")`: true. `Store.Transaction` opens a transaction and builds the bound store `tx` with an empty commit queue. `dataHooks.Begin` opens the write's operation with an empty `Values`.
3. `u.ToMap()` gives the row.
4. `dataHooks.BeforeCreate` builds a context with `Tx: tx` and calls `RunBefore(data.user.beforeCreate, row)`.
5. `DefaultDispatcher`: `checkPhase`, the point's rate-limit rules, then the handler. It returns the row with a column changed.
6. `checkColumns`, `normalizeUserRow(row)`, `u.FromMap(row)`, `tx.db.Create(ctx, u)`.
7. `dataHooks.AfterCreate` calls `RunAfterTx(data.user.afterCreate, u)`. The handler inserts a row of its plugin's table through `hctx.Tx.DB()`.
8. `dataHooks.AfterCreate` queues the dispatch of `data.user.created` with `tx.AfterCommit`.
9. The callback returns nil and the adapter commits. Both rows are durable.
10. `Store.Transaction` runs the queue: the callback calls `RunAfter(data.user.created, u)` with `Tx: nil` and the same `Values` the handlers in steps 5 and 7 saw.
11. `CreateUser` returns nil. `u` holds the stored user.

If the handler in step 7 returns an error instead: `RunAfterTx` returns it, `create` returns it, the adapter rolls back the user row, the queue is dropped, and `CreateUser` returns the handler's error. `u` still holds the id and the rewritten column of a row that does not exist.

When `CreateUser` is called on a store that is already bound to a transaction, step 2 joins it and step 9 does not commit. Steps 10 and 11 swap: `CreateUser` returns, and `data.user.created` fires when the caller's transaction commits, or never if it rolls back.

# **Adding data hooks to a table**

To make `accounts` fire data hooks:

1. Add the six point constants to `types/hooks/hooks.go` (`data.account.beforeCreate`, ...) and, if needed, a `HookValue...` key for the id.
2. Declare the six points in `CoreDeclareHookPoints` with the phases of the table in [2. Hook Taxonomy](<2. Hook Taxonomy.md>): the two `before...` points as before, the other four as after.
3. Add an entry for the table's schema name to `coreDataHookPoints`.
4. Make sure every write to the table goes through `Store.create` or `Store.update`. A store method that calls the adapter directly fires nothing.
5. Update `TestCoreDeclaresTheHookPointsItFires`, which counts the declared points, and the point reference in [`../../api/hooks.md`](../../api/hooks.md).

What changes for the table once the entry exists:

- every create and update opens a transaction, or joins the caller's
- a handler error can now fail those writes
- on MongoDB the write and its hooks may run more than once on a transient error

The session and token tables should not get an entry. Their managers already fire Tier 2 points around the same writes; see [2. Hook Taxonomy](<2. Hook Taxonomy.md>).

# **Limits to know**

- **Only `users`.** `accounts`, `sessions`, `tokens` and `rate_limits` fire no data hooks.
- **No delete points.** `Store.DeleteUser` calls the adapter directly. There are no `beforeDelete` or `afterDelete` points and no `store.Hooks` methods for them.
- **Writes through the adapter fire nothing.** `AuthContext.DB` and `Store.DB()` bypass the store's write paths and with them every data hook.
- **A plugin can't add data points to a table.** `coreDataHookPoints` is a package variable of `types/init`, and `Boot` passes it to `dataHooks` as it is. A plugin's own tables are written through the adapter and fire nothing unless the plugin fires points of its own.
- **The table is found by schema name.** An entry whose key does not match any model's `SchemaName()` never fires, and `checkDataHookPoints` does not notice, because it checks points and not table names.
- **No failed points.** A write that fails returns its error and fires nothing.

# **Design decisions**

### The store calls its own interface, not the dispatcher
**Context:** The store has to fire hooks around writes, and the dispatcher's types live in a package that imports the store.
**Options considered:**
- *Move the hook types below the store* (a package both import). The store could call the `Dispatcher` directly. `HookContext` holds an `*AuthContext`, which holds the store, so the cycle moves instead of going away, and the data layer would know about hook points, phases and requests.
- *An interface in `store`, in the store's terms, implemented in `types/init`.* One more type and an adapter. The store stays a data layer: it reports table writes and knows nothing about who listens.
**Decision:** The interface in `store`. It also makes the store testable with a small recording implementation and no dispatcher.

### `store.Hooks` has `Begin` and no committed methods
**Context:** A write's before, after and committed points should share one `Values` map. The store called `BeforeCreate`, `AfterCreate` and `CreateCommitted` separately, with nothing that told the implementation they belonged to one write. The committed call also ran with a different context than the other two.
**Options considered:**
- *An opaque handle.* `Begin` returns a value the store passes back to every later call. Every method gains a parameter.
- *`Begin` returns a context, and the committed methods stay.* The before and after calls are tied together. The committed call still can't be: it has to run with the context of the `Transaction` call, which does not carry the write's scope, and the store can't move a value it does not know from one context to the other.
- *`Begin` returns a context, and the implementation queues its own commit callback.* The after method captures what the committed dispatch needs and queues it with `Store.AfterCommit`, which is public already. `store.Hooks` loses two methods and the store loses the notion of a committed notification.
**Decision:** The third option. The store is left with two generic tools, a per-write context and a commit queue, and the adapter decides what to do with them.
**Revisit if:** another implementation of `store.Hooks` needs the committed notification and gets the "queue only after success" rule wrong. A helper in `store` could then wrap it.

The decisions about running data hooks inside the transaction and about the in-memory commit queue are recorded in [`../models/models.md`](../models/models.md#data-hooks-and-transactions).
